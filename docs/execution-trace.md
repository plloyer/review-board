# Execution evidence and scoped board consent

This is a partial delivery. The board-only native approval requirement is **not met**.
The board stores facts and an action-scoped owner vote; it cannot grant native execution
permission. Every recovery projection has `executable: false`. No recorded command runs,
no permission profile changes, and no session or alternate executor is opened.

The generic reducer is `server/execution-trace.js`, shared by HTTP, MCP and the rendered
board. Project-local adapters should emit this contract rather than copy its status rules.

Each card has `executionTrace` (schema 1, immutable events, currentActionId) and `execution`
(a derived view). The SHA-256 action digest binds these exact, ordered UTF-8 JSON fields:
`operation`, `command`, `cwd`, `destination`, `targetRef`, `version`, `threadId`, `effects`.
Effects are an explicit list, including an empty list when none are declared. A changed
scope creates a new action and retains old evidence without inheriting its vote. A prior
digest cannot be reselected to resurrect consent. Repeated action observations belong on
their original card; cross-card duplicates, including archived cards, are rejected.

Record one fact with `POST /api/messages/:id/execution-events`, or MCP
`record_execution_event {cardId, event}`. An event has stable `id`, `type`, `actionId`,
ISO timestamp `at` with timezone, and an explicit `source`, plus:

| type | Required evidence |
| --- | --- |
| observed | action; optional runtime: sandboxMode, approvalsReviewer, network, source |
| denied | reason (verbatim or null), reasonSource, provenance (unknown if unavailable), nativeReviewId (exact or null), attemptId (exact or null); optional after/before bounds |
| consent | decision approved/rejected, boardReceipt; records a board readback, never a native grant |
| attempt | attemptId; blocked after a denial while no native adapter is available |
| publication | attemptId plus receipt referencing actual remote version/ref readback; or origin external_observation, attemptId null, and independent receipt |
| activation | publicationEventId plus a distinct receipt referencing actual running-version readback |

The receipt strings reference evidence reported by the caller; the board cannot independently
verify a remote Git ref or running process. They are not cryptographic attestations. A
denial cannot prove publication; ambiguous attempt identity also blocks a publication claim.
Generic card approval, landing, closed, acknowledgment or archive are never publication
or activation evidence. Publication and activation stay independent of kanban state.
Publication/activation `origin` is owning_attempt (default) or external_observation;
`actor` is an exact observed identity or null. An independently observed publication
can follow a refusal without an invented successful retry. It requires an explicit receipt,
never clears the denial, and leaves the owning task's attempt count unchanged. An external
publication cannot claim the denied task's attempt ID. This records facts, not a recovery
permission or an alternate executor. The observer must read back the destination and exact
version before reporting the receipt; the trace does not perform that operation itself.

The board's dedicated consent button posts `POST /api/messages/:id/execution-consent`
with `{actionId, decision}`. Its timestamp is generated by the server. A stale digest is
rejected, and repeated identical decisions make no new event. The existing general review
button approves the card, not a recorded execution action. Historical votes can be imported
as consent observations with their original timestamp and board receipt.

The current board's human/agent labels describe input routes, not authenticated identities.
Its existing network API is not a trusted native approval client. No native receipt or
capability can be supplied in an event: unknown fields and native-grant event types fail.

Persistence uses the existing fsynced atomic card/journal write. Evidence is replayed once
per ID; conflicting reuse fails. A failed save restores the old trace and event cursor.
Chronology compares consent to the full denial interval, preserving unknown order. A vote
after a denial does not become a vote evaluated and denied. A vote before denial alone
does not prove that the reviewer saw it.

## Required product capability

The inspected local Codex CLI schema names `thread/approveGuardianDeniedAction` with
`threadId` and the serialized original `GuardianAssessmentEvent`. A local schema does not
establish availability on the owning durable task. Here neither that original event nor
a callable trusted registration surface is exposed. Official guidance describes narrow
same-context approval for one retry, still subject to automatic review:
[Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review).

Product support must expose retrieval of the original denial and a supported authenticated
client surface that binds the scoped board vote to that exact native event in its owning
task, returns a verifiable scoped receipt, and preserves automatic review and one-shot
consumption. Availability, matching identifiers, revocation, changed actions and consumed
grants must be verified before any executable recovery control is built. No adapter is
implemented against a guessed event or undocumented service behavior.

A possible Full Access/profile mismatch is under separate investigation. Effective sandbox
evidence is stored without inferring a cause or changing settings. Sandbox permission and
authorization of a particular external publication are separate facts. This trace does not
resolve the mismatch, nor justify an architectural migration or automatic authorization.

Run `node --test tests/*.test.js`. Tests use temporary data and ephemeral loopback servers.
No live board, publication, activation, LLM judge or paused game orchestrator is involved.
